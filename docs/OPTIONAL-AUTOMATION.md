# 可选：平台自动化（抖音等）

> ⚠️ **这一块默认不包含在仓库里，而且风险自负。**
> 自动读写第三方平台（点赞、评论、私信、关注）通常违反平台用户协议，
> 轻则限流，重则封号；代码也会因为页面改版随时失效。

## 为什么单独拿出来

这套东西本质是「浏览器自动化 + 风控对抗」，不稳定是常态：

- 页面 DOM 一改，选择器全废（今天就踩到：私信侧栏被搬进 shadow DOM，
  某个入口只在有未读消息时才短暂出现，抓不到就整条链路静默失效）
- 平台会给无头浏览器上验证、限流
- 频繁操作 = 账号风险

所以主仓库只放**稳定的那部分**（人格、记忆、语音、投递箱、流水），
自动化当成可选模块，谁要谁自己接。

## 如果一定要接，最低限度的规矩

1. **小号**，别用主号
2. **低频**：每条之间几十秒，每天有上限，别群发
3. **只用只读接口**做观察（推荐流、评论列表），写操作（评论/私信/关注）极少用
4. **无头浏览器用独立 profile**，别动你日常登录的那个
5. **失败即停**：报错就停手，不要连着重试（重试 = 更快触发风控）
6. 入口/选择器失效时，**如实报错**，不要"假装成功"

## 结构上它应该长在哪

```
终端层（第 3 层）
  └─ 浏览器自动化模块（独立进程）
       ├─ 读：只读接口 / 页面文本
       └─ 写：用户操作（低频、需确认）
容器层（第 2 层）
  └─ 通过「工具」调用上面的模块，并把结果写进流水
```

关键：**自动化模块永远不直接改人格文件或记忆文件**，
它只提供「看到了什么」，由大脑决定「要不要回、怎么回」。
这样即使某个平台改版，坏的只是"眼睛"，不会污染"她是谁"。

## 一个现实的建议

如果你只是想让 AI 有"生活感"，接一个能发消息的渠道（QQ/Telegram/Discord）就够了，
没必要去平台上做自动化。收益小、风险大、维护累。
