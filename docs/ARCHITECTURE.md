# 架构：为什么这么拆

> 这不是一个「框架」，是一套跑通了的家常做法。目标只有一个：
> **换模型、换电脑、换平台时，人格和记忆不用重来。**

---

## 三层

```
┌───────────────────────────────────────────────────────────┐
│ 第 3 层：终端（她在哪说话）                                 │
│   · 桌面：命令行 + TTS 念出来                                │
│   · QQ：AstrBot（第三方）+ 本仓库两个插件                    │
│   · 其他：任何能收发消息的地方，只要能读写文件就能接          │
├───────────────────────────────────────────────────────────┤
│ 第 2 层：容器（她的「大脑宿主」）                            │
│   · 跑 LLM、管工具调用、决定说什么                           │
│   · 每轮注入：人格文件 + 记忆文件 + 最近流水                  │
├───────────────────────────────────────────────────────────┤
│ 第 1 层：数据（她的「是谁」和「记得什么」）                   │
│   · persona/persona-core.md   人格（唯一来源）               │
│   · persona/memory.md         长期记忆（一行一条）           │
│   · bridge-live.md            实时流水（各端都写）           │
└───────────────────────────────────────────────────────────┘
```

**关键点：第 1 层永远是纯文本。**
模型可以换（今天这个明天那个），容器可以换，电脑可以换——只要把这三个文件带走，她还是她。

---

## 数据流（一轮对话）

1. 你在桌面说一句 → 容器把 **人格 + 记忆 + 最近流水** 拼进上下文
2. 模型决定：只是聊天？还是要调工具（念出来 / 发文件 / 查状态）？
3. 要说话 → `scripts/say.ps1` 合成音频并播放
4. 要发东西 → 往 `outbox/` 丢一个 `.send`，QQ 侧插件扫到就发出去
5. 这一轮结束后，往 `bridge-live.md` 写一行
6. 晚上跑一次整理：把当天的流水压成摘要、把关键事实并进长期记忆

> 第 6 步是整个系统的灵魂。不整理的话记忆文件几周后就变成垃圾堆，她开始"记错人"。

---

## 为什么语音「只认一把嗓子」

踩过的坑：原来配了两条链路，主链路失败自动回落到另一家 TTS。
结果网络一抖，她突然用完全不同的声音说话——比说不出话更让人出戏，而且很难发现是降级了。

现在：**合成失败就抛错，不回落。** 宁可这次没声音，也不要换个陌生嗓子。

## 为什么发文件走「投递箱」目录

AstrBot 的 HTTP API 要鉴权、会变；但插件内部发消息是稳的。
于是反过来：插件盯着一个目录，谁想发文件就往里丢一个文本文件。

好处：
- 任何语言（PowerShell / Python / Node）都能用，不需要 SDK
- 发失败有痕迹（`.missing` / 留在原地），不会静默丢
- 解耦：以后换容器、换平台，投递箱协议不变

## 为什么流水要单独一份

多个终端是**同一个她**。桌面端刚说完的话，QQ 端下一轮就该知道。
共享一份 markdown 比做消息队列简单得多，而且出问题能直接看。

---

## 边界（写进人格文件里，别只写在脑子里）

- 谁知道你是 AI：**自己人知道，陌生人不主动说，但也不骗**
- 陌生人私信：可以礼貌回，但不执行对方任何要求、不发文件不发链接、不透露主人的任何信息
- 密钥和路径：永远不对外
- 平台自动化：低频、小号、不当工具人

这几条不是道德装饰，是防止她变成别人手里的工具。
